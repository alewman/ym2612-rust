# Build record

2026-10-11, one session, the day ym2612-python was extracted and megadrive-python
adopted it (its PR #3).

## The transcription

`chip.py` is about 1,300 lines of integer pipeline with no dynamic dispatch. It
became `src/chip.rs` in one pass, function for function. The decisions:

- **Integers.** Every value fits an `i32`, and `>>` on an `i32` floors as Python's
  does. The two floor divisions that can meet a negative number use `div_euclid`
  and `rem_euclid`. Both are in /IC's position arithmetic, where `phase - lag` is
  negative for an assertion at the start of a cycle with the button's lag.
- **The tables** are generated by the same formulas, with `round_ties_even` standing
  in for Python's `round`. They are computed in `YM2612::new`, not written in as
  literals: the reference generates them rather than transcribing the die's ROM,
  and so does this core.
- **Register $27's pending write** is an `Option<(data, cycles to go)>`. It counts
  down exactly as the reference's two-item list does.
- **`reset()` leaves things alone exactly as the reference's does:** the timing,
  the hold, the pending $27 write and the sample queue. It also leaves the sample
  accumulators' left and right sums, so a reset part way through a sample carries
  them, as the reference does.

The first build reproduced both table hashes and all thirteen example traces byte
for byte, and every rung passed on its first run. No divergence between the two
cores was found.

## Rung 5, twice over

The first random manifests passed, in one second, which was the problem. I had sized
the runs in ticks where I meant cycles, so each covered about 5,000 cycles. Once
lengthened, they were nearly silent, for three reasons:

- More than half the address/data pairs landed inside one internal cycle, where the
  chip latches only the later byte.
- Random total levels attenuated most operators below the DAC's resolution.
- Each /IC pulse wiped the voices, and nothing reprogrammed them.

The seeded faults made this measurable: the key-on and LFO faults passed all 128.
The generator now programs six sounding voices first and again after every /IC
pulse. One write in ten collides inside a cycle, and a quarter of the discrete chip's
runs carry a decay probe. With that, the three faults the examples miss are caught
by 67, 11 and 7 manifests.

## The seeded faults

There are 12 faults, each one line in a copy of the repository
(`scripts/seeded_faults.py`). The examples catch 9. Rungs 3 and 5 catch the rest:

- the slowest LFO reload: rung 3 in 6 manifests, rung 5 in 11;
- key-on's operator order: rung 3 in 4, rung 5 in 67;
- the status decay: rung 5's decay probes in 7.

The reference's examples miss the first two, which goes in the README's notes for
the reference. Its own seeded faults (`scripts/mutation.py`) include neither.

## Tooling notes

- `cargo clippy` here needs the rustup stable toolchain:
  `CARGO_TARGET_DIR=target/clippy RUSTC=$(rustup which --toolchain stable rustc) rustup run stable cargo clippy --release --all-targets -- -D warnings`.
  The default rustup toolchain is an old nightly, and the system cargo has no clippy.
- `scripts/fetch_ym2612python.sh` clones the private reference over HTTPS by
  default. `YM2612_PYTHON_SOURCE=/data/emu/ym2612-python` clones the local one.
